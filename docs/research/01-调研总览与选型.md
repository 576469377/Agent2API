# Agent2API 调研总览与技术选型

> 调研日期：2026-09-15
> 结论优先级：本文所有关于 WorkBuddy 上游协议的结论，均以**本机真实请求实测**为准（见 [02-WorkBuddy上游协议逆向.md](02-WorkBuddy上游协议逆向.md)），参考仓库仅作为交叉验证。

---

## 一、项目定位

做一个**多平台 Agent 反向代理网关**：把各家 AI 编程 Agent 平台（WorkBuddy/CodeBuddy、Devin 等）的私有上游协议，统一翻译成标准 LLM API（OpenAI Chat Completions / OpenAI Responses / Anthropic Messages），对外暴露 OpenAI 兼容接口，让 Claude Code、Codex CLI、各类客户端零改造接入。

第一个目标：**workbuddy2api**。

---

## 二、参考项目横向对比

调研了 4 个直接相关的开源实现：

| 项目 | 语言 | 规模 | 定位 | 对我们的价值 |
|---|---|---|---|---|
| [hawklithm/workbuddy2api](https://github.com/hawklithm/workbuddy2api) | Python | ~5.8k 行 | 单账号、三协议转换、脱敏 | ⭐ **协议细节最全**（DSML 解析、脱敏词表、header 清单）。但有死代码、模型清单陈旧（2026-07 版本，与现网已不一致） |
| [Sliverkiss/workbuddy2api](https://github.com/Sliverkiss/workbuddy2api) | Go | ~11.3k 行 | 多账号池、调度、熔断、签到/积分 | ⭐ **工程架构最好**（realm 双站、pool/scheduler/session 分层）。是 Go 版架构的主要参考 |
| [Tom6814/WorkBuddy2API](https://github.com/Tom6814/WorkBuddy2API) | Python | 轻量 | 单文件 FastAPI 最小实现 | 仅作思路印证，无架构价值 |
| [WncFht/devin2api](https://github.com/WncFht/devin2api) | Go | 大型 | Devin → OpenAI/Anthropic | ⭐⭐ **多平台架构的最佳范本**。它的 IR 分层设计直接决定我们"多平台"怎么抽象 |

### 关键差异：上游是否标准

- **WorkBuddy**：上游 `POST /v2/chat/completions` **本身就是 OpenAI Chat Completions 兼容格式**（实测确认）。这是重大利好——请求侧几乎不需要转换，代理主要做「认证注入 + 流式规范化 + 非流式本地聚合 + 脱敏」。
- **Devin**：上游是私有 protobuf over Connect，必须做完整 IR 转换，devin2api 为此专门写了 `protoextract`/`protocensus` 逆向工具链（2300+ 行）。**我们不需要这些**。

## 三、核心结论速览（实测）

| 项 | 结论 |
|---|---|
| 上游 Base URL | [copilot.tencent.com](https://copilot.tencent.com)（`/v3/config` 返回的 `endpoint` 字段显式确认） |
| 聊天端点 | `POST /v2/chat/completions` |
| 模型清单 | `GET /v3/config`（需特定 UA，见下文） |
| **非流式** | ❌ **不支持**，返回 `{"code":11101,"msg":"Non-stream chat request is currently not supported"}` → 必须在代理侧本地聚合 |
| 流式格式 | 纯 `data:` 行 SSE，无 `event:` 行，`data: [DONE]` 终止 |
| **思考过程** | ✅ `delta.reasoning_content` 字段（**参考实现全部漏掉了这个**） |
| 工具调用 | 原生 `delta.tool_calls`（OpenAI 形态）+ DSML 文本兜底双通道 |
| 认证 | JWT Bearer，从实测 `workbuddy-desktop.info` 读取，可 refresh |
| 模型数 | 22 个（含 4 个代码补全专用模型，实际可用聊天模型约 15 个） |

## 四、三个参考项目的致命问题（我们不能照抄）

1. **模型清单全部过时**。hawklithm 仓库里的 `models_config.json` 是 2026-07 的快照，与今天 `/v3/config` 实拉结果差异很大（现网已有 `glm-5.3`/`glm-5.3-flash`/`kimi-k3-1`/`hy4-preview-f`，旧的 `glm-5.0`/`glm-4.7`/`deepseek-v3-2-volc` 已消失）。
   → **结论：模型清单必须运行时动态拉取 `/v3/config`，硬编码清单必然腐烂。**

2. **`models_config.json` 位置 bug**。hawklithm 代码读 `src/codebuddy_proxy/models_config.json`，但文件在仓库根目录 → 实际永远走硬编码兜底分支。

3. **脱敏（desensitize）是刚需，不是可选项**。上游有关键词级内容审核，Claude Code / Codex 的固定 system 模板里有大量 "DoS / exploit / credential testing" 等合规声明词，**会被误判拦截**。README 原文：不启用脱敏时「几乎每次请求都会被审核拦截」。

## 五、技术选型建议

### 5.1 语言：**推荐 Go**

| 维度 | Go | Python |
|---|---|---|
| 交付物 | 单二进制，无运行时依赖 | 需 venv / uv，部署摩擦大 |
| 流式并发 | goroutine 天然契合 SSE 长连接转发 | asyncio 可用，但背压/超时处理更易出错 |
| 生态先例 | devin2api、Sliverkiss 版均为 Go | hawklithm 为 Python |
| 多平台扩展 | 接口抽象 + 静态类型，重构安全 | 动态类型，大规模重构风险高 |
| 开发速度 | 略慢 | 略快 |

**推荐 Go 的核心理由不是性能，而是"这是个要长期加平台的项目"**——静态类型 + 显式接口能让第 2、第 3 个平台接入时不至于把第一个平台搞坏。

### 5.2 架构：借鉴 devin2api 的 IR 分层

devin2api 的可移植性来自三件事（合计不到 800 行）：

1. **零依赖 IR 包**（[`internal/llm`](../../internal/llm/)）—— 请求/响应的中间表示，不 import 任何上游或下游协议包
2. **两个极小的接缝接口** —— `Adapter{ Stream(), ListModels() }` 仅 2 方法；`ResponseStream{ Recv(ctx) }` 仅 1 方法
3. **结构化错误记录** `llm.Failure` —— 一次分类、全程携带，不在呈现层正则反推

**关键收益：N 个平台 × M 个下游协议，从 N×M 降到 N+M。** 加第二个平台时下游三个协议编码器一行不用改。

### 5.3 devin2api 里**不要**抄的部分

- `rateGate`（584 行）：分钟桶对齐、drip 探针——完全是对 Devin 私有限流器的过度拟合。第一版只需令牌桶 + 简单冷却。
- `protoextract`/`protocensus`（2300+ 行）：逆向 protobuf 用，我们上游是 JSON，不需要。
- `debuglog` 六阶段落盘（1100 行）、Web 面板（1900 行）、WebSocket：延后。

## 六、风险与合规

- 本项目为**非官方逆向代理**，上游协议无稳定性承诺，可能随时变更（参考项目 README 均明确提示）。
- 仅限本人授权账号、实测/私有环境使用。
- 三个已知上游不稳定性信号：
  - 模型清单会随版本更替（本次调研已发现参考实现清单全部过期）
  - 上游存在 `/console/chat/completions` 与 `/v2/chat/completions` 双路径分叉（Sliverkiss 注释：global realm 先打前者，404/405 回落后者）
  - 上游偶发返回 GBK 编码（hawklithm 注释），响应解码需多编码兜底

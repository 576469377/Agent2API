# 定位 ZCode 的 400 参数错误

[文档导航](README.md) · [故障排查](troubleshooting.md)

`the request parameters were rejected by the model provider` 表示上游模型供应端拒绝了这次请求，但这句通用错误没有指出具体字段。它不能单独证明某个模型不可用，也不能证明是输出上限、思考参数或历史工具调用导致。

如果问题只在旧对话继续执行、调用工具或切换模型后出现，需要对比失败请求的历史结构和参数。其他机器上短请求成功，不能证明原对话已经修复。控制台里的输入 / 输出 Token 为 0 表示尚未取得用量，不表示请求里没有输入；失败详情的账号为 `—` 也不能据此判断账号没登录。

## 先统计历史图片

2026-10-13/14 用户提供的真实请求对照实验发现：国际版 `hy3` 的 200/201 张、`step-5-preview` 的 60/61 张分别是受理 / 拒绝边界，计数包括工具结果嵌套图片。国内版和其他模型不套用这些值；测到 201 / 248 张成功只说明该次请求受理，不能推断无限制。

新版后端会在转发前按[图片护栏配置](configuration.md#单请求图片数量护栏modelsimage_limits)拦截已知超限请求。控制台调用详情提供 `image_count` 和当次生效的 `max_images`，日志行提供 `images=N`；旧指标未记录的图片数量显示「未记录」。模型详情和 `/api/models` 的 `image_limit` 显示有效护栏及来源。

不要只匹配英文就判定超限：Step 的 `Invalid request parameters` 同时出现在图片超限和图片数据非法的实测中；Hy3 的 `the request parameters were rejected by the model provider` 也需结合计数。国内版 `Please start a new conversation, replace the image, and try again.` 出现在图片数据非法的实测中，但仍不能把文案当作唯一诊断依据。未命中已启用护栏的超限条件时，保留英文并附「原因未知」与图片数量，不断言超限或坏图。

处理时先看图片数量与实际平台的护栏：超限可开新对话、减少历史图片或选择适用模型；未超限仍失败时，再核查图片数据及其他参数。网关不会静默删除历史图片。

ZCode 在默认 `reject` 模式下反复发「继续」不会减少历史图片。若接受丢弃上游视野中最旧图片，可显式启用[旧对话续聊策略](configuration.md#旧对话超限后的续聊策略modelsimage_overflow_policies)：每次独立保留最近图片，原文字与工具结果保留，本地对话不变，并记录省略数量。若清理到护栏以内后仍遇到含糊 400，只标注原因未知，不再误判成原始图片数量超限。

## 历史图片重复上传与等待

WorkBuddy 国际版 `deepseek-v4.1-flash` 会将不小于 8 KiB 的内嵌 PNG、JPEG、GIF、WebP 原图上传到 WorkBuddy 自己的私有附件存储，聊天请求改用有时效的签名下载链接。图片文件保持原始字节；每张图片出现的位置、文字历史和工具调用关系继续完整发送。其他平台或尚未验证的模型继续使用原有传输方式。

引用缓存按账号和上游地址隔离，合并并发上传，并在系统缓存目录 `Agent2API/workbuddy-images` 保存引用元数据，不保存原图。重启后先检查文件；临近签名过期时续签，文件已不存在时重新上传原图。附件服务不可用时保留原始内嵌图片，不因这项优化删减上下文。

控制台的“正在准备历史图片”显示处理进度、图片引用和复用数量；进入“正在上传请求”后显示聊天请求体的实际发送阶段。首次仍需上传原图，后续轮次主要发送链接。上游读取图片、排队和生成的时间仍包含在首段等待中；请求体缩小不代表这些时间会按相同比例缩短。

## 在出错机器取得结构摘要

无需停止已有反代。需要 Python 3.9+，在 Agent2API 项目目录运行：

```powershell
python scripts/diagnose-proxy.py --upstream http://127.0.0.1:8787 --port 8790
```

1. 暂时将 ZCode 对应供应商的 Base URL 改为 `http://127.0.0.1:8790/v1`，保留原 API Key 和协议。
2. 等待客户端配置生效，在原来失败的对话里重试一次。每次只检查一个模型，方便对应摘要。
3. 若仍返回 HTTP 400，终端会输出一行 JSON 结构摘要，可以复制这行和 ZCode 的错误详情进行排查。
4. 完成后，将 Base URL 恢复原值，再关闭诊断程序。

此脚本是临时的本机转发入口。只允许回环地址，转发请求正文和必要请求头，每次请求只发送一次，没有自动重试；流式数据边读边转发。原反代、账号池和凭证文件继续由原进程管理。

摘要只包含已知的数值参数、受限枚举、消息 / 内容块数量及字节数、工具调用配对计数。不会记录模型或会话标识、请求头、密钥、正文、图片、工具名称、工具参数、工具结果正文或思考签名，也不会保存原始请求 / 响应文件。上游错误正文同样不会写入诊断日志。脚本针对 HTTP 错误生成摘要；HTTP 200 流内报错仍以控制台调用详情为准。

## 如何理解摘要

| 字段 | 用途 |
|---|---|
| `image_count` | 先检查图片总数（包括工具结果嵌套图片），再比较实际平台 / 模型的有效护栏 |
| `max_tokens`、`thinking_type`、`reasoning_effort` | 检查实际请求的输出、思考配置，而非只看客户端模型配置 |
| `message_count`、`roles`、`content_blocks` | 检查旧对话包含多少历史消息和哪些内容类型 |
| `body_bytes`、`text_bytes`、`system_bytes`、`tool_schema_bytes` | 比较失败请求和短请求的体积；**字节数不是 Token 数** |
| `tool_call_count` / `tool_result_count` | 检查调用与结果的数量 |
| `orphan_tool_results`、`unanswered_tool_calls` | 检查缺少前置调用或结果的历史结构 |
| `duplicate_tool_calls`、`duplicate_tool_results`、`missing_tool_ids` | 检查重复或缺失的工具标识 |
| `mixed_tool_result_user_messages` | 检查工具结果和普通用户内容混合的消息 |

这些计数是结构观察，不会据此自动删除历史、填造结果、关闭思考或改写输出预算，也不能直接认定某个计数就是 400 的原因。需要结合出错机器的实际参数、版本以及一次复现来确认。
